# OCR 워커 운영 (각자 실행 · 공용 큐)

워커는 대기열(SQS)에서 사진 분석 작업을 가져와 S3 사진을 읽고, Bedrock AI에 분석을 요청한 뒤 DynamoDB에 결과를 저장하는 백그라운드 프로그램입니다. AI 모델 자체는 Bedrock에 있고, 워커는 분석 요청과 결과 저장을 맡습니다.

## 기본 원칙

팀원은 **같은 승인된 OCR·공통 코드와 실제 Bedrock 모델 설정으로 각자 워커를 실행**할 수 있습니다. 다른 사람의 워커가 이미 켜져 있어도 실행할 수 있고, 한 사람이 PC를 꺼도 남은 워커가 처리를 이어갑니다.

워커는 내 사진만 처리하는 것이 아니라 **공용 SQS에서 받은 모든 팀원의 사진**을 처리합니다. SQS가 여러 워커에 작업을 나눕니다. 모든 워커가 꺼지면 분석이 대기하고, 큐에 남아 있는 요청은 다시 켜졌을 때 처리됩니다.

**2026-10-30부터 EKS의 ocr-worker 1개가 항상 공용 큐를 처리합니다.** 로컬 워커를 꺼도 분석은 계속되며, EKS 워커는 `main` 머지 때 자동 배포로 새 코드로 바뀝니다. 그래서 OCR·공통 코드를 바꾸는 PR은 머지되는 순간 EKS 분석 버전도 바뀝니다 — 머지 전 팀에 알리고, 로컬 워커 실행자도 같은 버전으로 갱신합니다.

같은 PC에서 워커를 여러 번 켤 필요는 없습니다. SQS는 재전달이 가능하고 현재 코드에는 중복 분석을 완전히 막는 보장이 없으므로, 워커가 여러 개라는 이유로 정확히 한 번 처리된다고 가정하지 않습니다. 중복 분석·동시 저장은 추가 검증 대상입니다.

## 실패·재시도와 중복 처리

- 정상 완료하면 결과를 저장하고 해당 SQS 메시지를 삭제합니다.
- 추출 구간의 AWS `ClientError`는 수신 횟수 기준 최대 3회 시도합니다. 한도 전에는 `queued`로 되돌리고 메시지를 남기며, 한도에 도달하면 `failed`와 사유를 저장하고 메시지를 삭제합니다.
- 영수증이 아닌 사진·모델 응답/값 오류는 즉시 `failed`로 저장하고 메시지를 삭제합니다. 증빙이 이미 삭제됐다면 메시지만 버립니다.
- `seed_dev_data.py`가 넣은 시드 증빙(`seed` 표시)은 사진이 `incoming/`에 있어 큐에 들어오지만, 워커가 모델을 부르지 않고 메시지만 지웁니다. 이 확인이 없는 예전 워커는 시드 증빙을 실제로 분석해 Bedrock 비용이 나고 저장된 값을 바꾸므로, 시드를 넣기 전에 켜진 워커가 최신 `main`인지 확인합니다.
- 예상하지 못한 메시지 처리 오류는 로그를 남기고 한도 전에는 메시지를 남기며, 한도에서는 삭제합니다. 이 경로에서 항상 `failed` 상태가 저장되는 것은 아니므로 화면이 대기·처리 중 상태에 머물면 로그도 확인합니다.
- SQS 설정은 가시성 제한 **180초**, 원래 큐 보관 **24시간**, DLQ 보관 **14일**, `maxReceiveCount=3`입니다. DLQ는 삭제되지 않은 메시지가 수신 한도를 넘길 때 적용되며, 코드가 삭제한 실패 메시지까지 모두 보관하지는 않습니다. 모든 워커가 꺼진 상태로 보관 기간을 넘기면 요청이 계속 남는 것은 아닙니다.
- 오래 걸리는 처리·프로세스 종료·재전달로 같은 메시지가 다시 처리될 수 있습니다. 현재 워커는 가시성 제한 연장이나 분석 중복 실행 차단을 완전히 보장하지 않습니다. 여러 워커 운용 시 중복 분석과 동시 저장 가능성을 고려합니다.

## 실행 전 확인

1. [작업 시작 지침](../AGENTS.md)에 따라 최신 `main`을 받고 작업 브랜치를 만듭니다. 기존 워커는 코드·설정 갱신 전에 종료합니다.
2. 팀이 사용하는 승인 기준은 원칙적으로 최신 `main`입니다. 작업 브랜치가 달라도 `services/ocr-worker/`, `services/common/`, `services/uv.lock` 등 분석에 영향을 주는 코드·의존성은 승인된 기준과 같아야 합니다. 웹만 수정하는 브랜치에서도 이 조건이면 실행할 수 있습니다.
3. `services/.env`의 AI 설정을 아래와 같이 맞춥니다. 환경 파일을 공유하거나 커밋하지 않습니다. 생성 스크립트 `make_env.py`도 이 기본값을 사용하지만 기존 파일은 자동으로 덮어쓰지 않습니다.

```dotenv
RF_AI_MODE=bedrock
RF_EXTRACT_MODEL=global.anthropic.claude-sonnet-5-5
RF_CHAT_MODEL=global.anthropic.claude-haiku-5-5
```

추출 모델은 OCR용 Sonnet, chat 모델은 챗봇용 Haiku입니다. 공용 테이블·버킷·큐도 팀 환경 파일 생성 스크립트가 조회한 값을 사용합니다. 터미널에 별도로 지정한 환경 변수는 `.env`보다 우선할 수 있으므로 실제 읽히는 값도 확인합니다.

프로젝트 루트에서 승인 기준과의 분석 관련 차이를 확인합니다. 차이가 있으면 워커를 켜지 않고 아래 수정 절차를 따릅니다. `origin/main`은 최신 코드를 받은 상태여야 합니다.

```bash
git status --short -- services/ocr-worker services/common services/uv.lock services/pyproject.toml
git diff origin/main -- services/ocr-worker services/common services/uv.lock services/pyproject.toml
```

`services/`에서 필요한 설정만 출력해 확인할 수 있습니다. 이 명령은 AWS를 호출하지 않습니다.

```bash
uv run python -c 'from receiptflow_common.config import get_settings; s=get_settings(); print(s.ai_mode, s.extract_model, s.chat_model)'
```

예상 출력은 `bedrock global.anthropic.claude-sonnet-5-5 global.anthropic.claude-haiku-5-5`입니다. 코드 버전·설정의 팀원 간 일치를 자동으로 강제하는 기능은 없으므로 각자 확인합니다. 설정을 바꿨으면 실행 중인 워커를 재시작해야 적용됩니다.

## 실행과 종료

기본 실행은 [로컬 개발 안내](local-setup.md#5-실행-각자-터미널-2개)를 따릅니다. 각자 `services/`에서 `bash scripts/dev.sh`를 실행하면 백엔드 3개와 워커가 함께 켜집니다.

- 워커 제외: `WORKER=0 bash scripts/dev.sh` — 화면·API만 작업하거나 OCR·공통 코드를 수정할 때.
- 워커만 추가 실행: `uv run ocr-worker` — API는 이미 켜져 있고 워커만 꺼져 있을 때.
- 시작 로그: `ocr-worker started (ai_mode=bedrock, model=global.anthropic.claude-sonnet-5-5)` 확인.
- 종료: 가능하면 진행 중 처리가 끝난 뒤 해당 터미널에서 Ctrl+C. 다른 워커가 남아 있으면 작업은 이어지며 마지막 워커를 끌 때는 팀에 알립니다.

## OCR·공통 코드나 모델을 수정할 때

1. **내 워커를 먼저 종료합니다.** 변경 대상·테스트 계획을 팀에 알리고 작업 브랜치에서 수정합니다. 나머지 서비스가 필요하면 `WORKER=0 bash scripts/dev.sh`를 사용합니다.
2. **공용 큐에서 수정 중인 코드나 mock 워커를 실행하지 않습니다.** 사진은 `make_sample_receipt.py`로 만든 합성 이미지만 사용하고, 기본 검증은 아래 moto 테스트로 수행합니다. moto 테스트는 실제 AWS에 쓰지 않습니다.
3. 실제 Bedrock 검증이 필요하면 공용 큐 소비 없이 합성 평가 스크립트로 추출 함수를 검사합니다. [모델 평가 안내](model-eval.md)를 따르며 실제 모델 비용이 발생합니다. 큐까지 포함한 mock·부하 테스트는 별도 테스트 리소스가 준비된 경우에만 수행합니다. 팀원별 큐 분리는 현재 자동 제공되지 않으며 AWS 리소스가 필요하면 인프라 담당자가 Terraform으로 준비합니다.
4. API·필드·상태가 바뀌면 먼저 `contract.md`를 합의하고 관련 서비스도 수정합니다. 프롬프트 변경은 `PROMPT_VERSION`을 올리고 최신 평가 수치·조건을 갱신합니다.
5. 담당자 리뷰·필수 CI 통과 후 PR을 머지합니다. **공용 버전을 전환하기 전에 기존 워커 실행자에게 종료를 요청**하고, 로컬·EKS에서 서로 다른 분석 버전이나 모델이 섞이지 않도록 모두 갱신합니다. 진행 중인 처리는 가능한 한 마친 뒤 전환합니다.
6. 각자 최신 코드를 반영하고 `uv sync --frozen` 및 AI 설정 확인 후 워커를 재시작합니다. 미커밋 변경은 임의로 덮어쓰지 않습니다. 합성 사진으로 공용 흐름의 분석 완료를 확인한 뒤 팀에 완료를 알립니다.

기본 검증 명령은 `services/`에서 실행합니다.

```bash
uv run ruff format --check .
uv run ruff check .
uv run pytest
```

## 분석이 대기하거나 실패할 때

- 내 워커 시작 로그의 모드·모델을 확인하고 오류 로그를 봅니다. 여러 워커를 추가 실행하는 것만으로 인증·모델 오류가 해결되지는 않습니다.
- AWS 세션 만료라면 `aws login --profile team-admin` 후 다시 확인하고 필요하면 워커를 재시작합니다.
- `RF_QUEUE_URL`·리전·테이블·버킷 설정이 팀 환경과 맞는지 확인합니다. 비밀값이나 환경 파일 전체를 단체 대화방에 붙이지 않습니다.
- 다른 정상 워커가 있으면 내 워커가 없어도 분석될 수 있습니다. 모든 워커가 꺼진 경우 위 조건을 확인한 뒤 각자 켤 수 있습니다.
- 큐에 남아 있는 요청은 워커가 처리하므로 대기 중이라는 이유로 반복 업로드하거나 다른 사람의 요청을 삭제하지 않습니다. 실패 상태의 원인은 로그와 오류 메시지로 구분합니다.
